# ADR-001: Morphology Index Design

- **Status:** Accepted (Decisions 1, 2 and 3). The open questions are still proposals.
- **Date:** 2026-10-26
- **Scope:** `src/backend/priscianus/morphology/` and the `make data` build step

## Context

The morphology index is the ground truth that every grammatical claim is checked against (see [plan.md](../plan.md), section 2). The verifier queries it to label each claim VERIFIED, AMBIGUOUS, CONTRADICTED or UNKNOWN. The LLM reaches it through the `lookup_form`, `inflect` and `list_lemmas` tools.

Requirements:

- **Operations.** Four operations:
  - `analyse(form)`: return every parse of a form.
  - `inflect(lemma, features)`: return the form(s) for a lemma and a feature set.
  - `list_lemmas(filters)`: find lemmas by part of speech, inflection class and frequency band.
  - A coverage check (`has_lemma` or equivalent): the verifier must be able to tell "not a Latin form" (CONTRADICTED) from "not in the index" (UNKNOWN).
- **Ambiguity.** `analyse` returns every analysis. A claim is correct if it matches any one of them.
- **Feature schema.** Every analysis uses Universal Dependencies (UD) feature names (`Case`, `Number`, `Gender`, `Person`, `Tense`, `Mood`, `Voice`, `VerbForm`, `Degree`), so analyses compare directly with treebank gold data.
- **Independence for the eval.** Ground truth should come from data, not from rules written in this repo. Otherwise bugs in those rules are counted as "correct" in every eval result.
- **Speed is not a design driver.** A sentence needs about 20 lookups, each taking microseconds, while the LLM call takes seconds. Choose for correctness, traceability and ease of debugging.
- **Licence.** Wiktionary data is CC BY-SA 4.0, so any database built from it and published must also be CC BY-SA (see [DATA_LICENCES.md](../../DATA_LICENCES.md)).

## Decision 1: Source of forms

### Options considered

| Option | Benefits | Downsides |
|---|---|---|
| **A. Store every form.** Expand Wiktextract inflection tables into one row per (form, lemma, features). | Simplest to build. Lookup is an indexed equality match. Every row traces back to a Wiktionary page. Keeps macrons. `analyse` and `inflect` read the same table in opposite directions. | Covers only lemmas that have a Wiktionary inflection table. Wiktionary's errors become ground truth. Large row count (estimated at a million or more; measure it). Participles multiply rows. |
| **B. Generate forms from rules.** Store principal parts and inflection class, and build forms with stem + ending rules (as Whitaker's Words and Collatinus do). | Small data. Covers any lemma whose principal parts are known. | Means rewriting Whitaker's Words. Irregular verbs (*sum*, *ferō*, *eō*), defective words and stem changes need special cases. Bugs in the rules become ground truth, which breaks eval independence. Analysis needs ending-stripping, which over-generates. |
| **C. Hybrid.** Stored forms first, then a fallback source (Whitaker's Words, or rules later), with every analysis tagged by source. | Fills coverage gaps and lowers the unverifiable rate. Disagreements between sources are useful data. | Two tag sets to map to UD. Needs a policy for disagreements. More to test. |
| **D. Wrap an external analyser** (Whitaker's Words, Morpheus) as a subprocess or service. | Little to build. Mature coverage. | Opaque and harder to deploy. Output must be parsed and mapped. Morpheus licence is unclear. Whitaker's Words has no macrons. The core of the project is outsourced. |
| **E. Finite-state transducer** (pyfoma, HFST; LatMor is an existing Latin one). | Standard in computational morphology. One machine does analysis and generation. Compact. | Steep learning curve. Weak Python tooling. Hard to debug. Poor at database-style queries such as "list 3rd-conjugation verbs". More than this project needs. |

### Decision

**Build option A now, and design it so it can become option C later.**

- Every lemma and analysis row has a `source` column (`wiktionary` for now).
- Callers depend on an interface, not on SQLite directly (see Decision 3), so a fallback source can be added without changing the verifier or the LLM tools.
- A fallback source is not in scope for milestone 1. Add it when the eval shows the unverifiable rate is high enough to matter (milestone 5 at the latest).
- Option B is not ruled out, but if it is built it is a cross-check against A, not ground truth.

## Decision 2: Schema layout

### Options considered

| Option | Benefits | Downsides |
|---|---|---|
| **One flat table**: form, lemma and features in each row. | Simplest. Easy to query by hand. | Lemma data repeated on every row. Lemma-level filters are awkward. |
| **Lemmas table + analyses table with typed feature columns.** One nullable column per UD feature, with values checked against an allowed list. | Readable SQL. `inflect` and `list_lemmas` are simple. NULL means "feature doesn't apply", which is distinct from every real value. | Adding a feature needs a schema change. |
| **Feature bundle as a UD string** (`Case=Abl\|Number=Plur`). | Compact. Matches treebank FEATS strings directly. | Matching on part of a bundle ("any ablative") needs string parsing or `LIKE`. |
| **Entity-attribute-value** (`analysis_id, feature, value`). | Fully flexible. | Slow, awkward joins, hard to read. |

### Decision

**Use a lemmas table plus an analyses table with typed feature columns.** Starting sketch (column names may change during implementation):

```
meta(key, value)              -- schema version, Wiktextract dump date, build hash
lemmas(id, lemma, lemma_display, pos, infl_class, freq_band, source)
analyses(id, lemma_id, form_display, key_loose, key_macron,
         case, number, gender, person, tense, mood, voice, verb_form, degree, source)
INDEX on analyses(key_loose), analyses(lemma_id), lemmas(pos, infl_class, freq_band)
```

`infl_class` and `freq_band` belong on `lemmas` from the start, because the drill filters and the eval's stratification need them.

## Decision 3: Runtime and interface

### 3a. Build and ship the index

| Option | Benefits | Downsides |
|---|---|---|
| **Read-only build output.** `make data` builds `morphology.db` in one go. The application opens it read-only. | Reproducible: the same dump and code give the same file, and the build hash in `meta` ties eval results to an exact index version. Runtime bugs cannot corrupt ground truth. No migrations, locking or backups. Many readers can share the file safely. | Every fix to the data means a rebuild. Nothing can be added at runtime; user-reported forms would need a separate writable store. The file is a large binary that must stay out of git. |
| **Live, writable database** (SQLite or Postgres with migrations, edited in place). | Individual rows can be fixed or added quickly. | Ground truth can drift or be corrupted at runtime. Eval results can't be tied to a fixed index version. Needs migrations and backups. |

Shipping the file:

| Option | Benefits | Downsides |
|---|---|---|
| **Built into the Docker image.** | Self-contained, so code and index can't get out of step. Fast start-up with no network dependency. | Larger image. Every index update means building and pushing a new image. |
| **Downloaded at start-up** (from S3 or GitHub Releases). | Smaller image. The index can be updated without rebuilding the image. | Start-up depends on the download location being reachable. Needs a version or hash check to avoid code and index mismatches. Slower cold starts. |

### 3b. How callers reach the index

| Option | Benefits | Downsides |
|---|---|---|
| **A typed `Protocol` interface** (`MorphologyIndex`) with typed results (`Analysis`, `Features`, `Lemma`). `SqliteIndex` is one implementation. | Makes the move from A to C cheap: a fallback implementation can be added without changing the verifier. Verifier tests can run against a small in-memory fixture. Normalisation and enclitic handling live in one place that callers can't skip. Typed results carry mypy strict checking across the boundary. The milestone 6 MCP server can reuse the interface. | More code up front. Risk of designing the interface before any caller exists. SQL is hidden from callers when debugging. Ad-hoc queries need a new method. |
| **Direct SQLite access** from the verifier and tools. | Fastest to write for milestone 1. | Couples every caller to the schema and to SQLite. A fallback source means changing every caller. Tests need a built database. |

### Other storage engines considered

- A Python dict loaded at startup is fastest, but likely uses hundreds of MB to a GB of memory at this row count.
- DuckDB with Parquet adds nothing for point lookups.
- SQLite stays the default.

### Decision

- **The index is a read-only build output.** `make data` produces `morphology.db` and records the schema version, source dump date and build hash in `meta`. The application opens it read-only (SQLite `mode=ro`). The file is never committed to git.
- **The database is built into the Docker image**, so code and index are always deployed together. Reconsider downloading at start-up if the image size becomes a problem or the index starts changing more often than the code.
- **Callers use a typed `Protocol` interface.** The verifier, the LLM tools and the API depend only on `MorphologyIndex` and its typed results, never on SQL or raw rows.
- **The interface grows with its callers.** Milestone 1 starts with `analyse` and `has_lemma`, which is what the verifier needs. `inflect` and `list_lemmas` are added when the drill features need them, so their signatures are shaped by a real caller.

## Open questions

These need a decision before or during milestone 1. Each item has a proposed answer.

- **Participles.** UD treats participles as `VERB` with `VerbForm=Part` plus case, number and gender, with the verb as lemma. Wiktionary also gives participles such as *amātus* their own entries. *Proposed:* store declined participle forms under the verb lemma to match the gold data, and measure how much this adds to the row count.
- **Lookup keys.** *Proposed:* store two keys, using the same normaliser module at build time and at query time.
  - `key_loose`: no macrons, u/v and i/j folded, lowercase. Used for treebank and user input.
  - `key_macron`: keeps vowel length. Used when a claim includes macrons.
- **Ecclesiastical spellings.** Folding *ae → e* at query time is lossy and causes false matches. *Proposed:* expand spelling variants at build time into a `spelling_variants(variant_key, canonical_key, kind)` table, or into extra key rows tagged with the variant kind. This also allows reporting Classical and Ecclesiastical results separately.
- **Enclitics.** *Proposed:* handle *-que*, *-ne* and *-ve* in the query layer, not in the data. Look up the whole form, then the form with the enclitic removed, and return both result sets marked. Words such as *itaque*, *neque* and *atque* still match as whole words.

## Consequences

- Coverage is limited to Wiktionary until a fallback source is added. The eval reports the unverifiable rate separately so that coverage gaps are not counted as model errors.
- Mapping Wiktionary tags to UD features is a single module, written in milestone 1.
- The built database is a derived CC BY-SA work. It must be attributed, and any published copy keeps that licence.
- Using a typed-column schema means adding a new UD feature needs a migration. That is acceptable because the feature set is small and fixed.
- Fixing a bad Wiktionary row means changing the build (for example with an override file) and rebuilding, not editing the database.
- Every index update means building a new Docker image.
- Verifier tests use an in-memory `MorphologyIndex` fixture and do not need `make data`.
