# ADR-005: Tutor Web App Design

- **Status:** Proposed
- **Date:** 2026-11-17
- **Scope:** the new `src/backend/priscianus/tutor/` package, the HTTP layer in `priscianus.api`, the index changes M4 needs (`infl_class`, `freq_band`, `list_lemmas`), the front end's contract with the API, the daily limits, deployment and the CI smoke eval

## Context

Milestone 4 turns the M3 pipeline into an app: explain, drills, grading, trust badges, public hosting. [ADR-004](ADR-004.md) fixed how claims are checked; this ADR fixes what the app builds on top. Every figure below comes from a command run on the current index (build `8081e7a9`, 278 MB), on the committed eval reports, or is marked as an estimate.

Findings from the index that shaped the decisions:

| Finding | Evidence | Consequence |
|---|---|---|
| 15,672 of 23,781 `verb` lemmas are participles (they have a `base_lemma`). Only 8,109 are real verbs. | `lemmas` grouped by `pos` and `base_lemma IS NULL` | `list_lemmas` must skip lemmas with a `base_lemma`, or "10 verbs" returns *abditus* and *accusans*. The pool is 34,935 lemmas. |
| `infl_class` and `freq_band` are empty for all 61,404 lemmas. 611 are deponent. | `count(infl_class)`, `count(freq_band)` | Decisions 4 and 5. |
| Nouns carry gender in only 106 lemmas (2,812 of 204,206 noun analyses). | `analyses.gender` by `pos` | A drill cannot filter by noun gender. See Decision 4. |
| *amo*, 3rd plural perfect active indicative has 3 forms (*amāvērunt, amārunt, amāvēre*). The index writes that tense as `Tense=Past, Aspect=Perf`. | `inflect("amo", ...)` | Several accepted answers are normal. Drill code must use the tool executor's feature translation, not raw `inflect`. |
| `inflect("is", {"Case": "Voc"})` returns `["-"]`. 114,896 of 2,152,654 analyses have form `-`. Only 1 lemma has nothing but `-`. | `inflect`, `analyses.form_display` | #99 fixes the build. Until then the app goes through the tool executor, which filters them. |
| *virumque*, *neque* and *amatne* have no analysis. *virum* has 3. | `lookup_form` | The index does not split enclitics (*-que*, *-ne*, *-ve*), and *neque* is not in it at all. See Decision 2. |
| `key_loose` maps *AMĀVĒRUNT*, *amaverunt* and *amāvērunt* to one key, and *Julius* to the same key as *Iulius*. | `normaliser` | Grading can reuse it (Decision 6). |
| *canō* has 1 stored spelling and *cānō* has 4, for the same lemma. | `analyses` for *cano* | The index's vowel lengths are not reliable enough to grade on. |

## Decision 1: The API

Three AI endpoints, one free endpoint, one health check. All bodies are JSON.

| Endpoint | Calls a model? | Counts against the daily limit? |
|---|---|---|
| `POST /api/explain` | Yes (Decision 2) | Yes |
| `POST /api/drills` | Yes (Decision 3) | Yes |
| `POST /api/grade` | **No** (Decision 6) | No |
| `POST /api/feedback` | Yes (Decision 6) | Yes |
| `GET /health` | No | No |

**Claim object**, shared by explain and feedback. It wraps `verifier.claims.Claim` and the verdict, as ADR-004 Decision 1 allows:

```json
{"form": "rēgī", "lemma": "rex", "upos": "NOUN",
 "features": {"Case": "Dat", "Number": "Sing"},
 "state": "ambiguous",
 "other_readings": [{"lemma": "rex", "pos": "noun", "form": "rēgī", "features": "Case=Loc|Number=Sing"}]}
```

`features` leaves out `"None"` values. `state` is one of the four states of ADR-004. `other_readings` are the index readings that do not match the claim (at most 50, the cap of ADR-004 Decision 2). They are empty for `verified` and `unverifiable`.

**Explain.** Request `{"text": "Arma virumque cano."}`. Response:

```json
{"text": "...", "model": "claude-sonnet-5-5", "prompt_id": "explain-v1", "dropped_claims": 0,
 "words": [{"token": "virumque", "claim": {"...": "..."}, "note": "enclitic -que"},
           {"token": "xyzzy", "claim": null, "note": "not_explained"}]}
```

`words` has one entry per word typed, in order.

**Drills.** Request `{"request": "10 perfect-tense verbs from the 3rd conjugation", "count": 10}`. `count` is optional (default 10, at most 10). `request` is at most 200 characters. Response:

```json
{"message": null, "shortfall": 0,
 "items": [{"lemma": "rego", "pos": "verb",
            "features": {"Person": "3", "Number": "Plur", "Tense": "Past", "Aspect": "Perf", "Mood": "Ind", "Voice": "Act", "VerbForm": "Fin"},
            "prompt": "Give the 3rd person plural perfect active indicative of rego."}]}
```

`prompt` is built by code from lemma and features, never written by the model, so it cannot say anything false about the item. There is no answer key in the response (Decision 3).

**Grade.** Request `{"lemma": "rego", "pos": "verb", "features": {...}, "answer": "rexerunt"}`. Response:

```json
{"correct": true, "accepted": ["rēxērunt", "rēxēre"],
 "answer_is": [{"lemma": "rego", "form": "rēxit", "features": "Mood=Ind|Number=Sing|Person=3|Tense=Past|Aspect=Perf|VerbForm=Fin|Voice=Act", "same_lemma": true}]}
```

`answer_is` lists what the typed form is, from `lookup_form`, when it is a real form that is not accepted. It is empty if the form is unknown.

**Feedback.** Same request as grade. The server grades again by itself and tells the model the result. Response `{"grade": {...as above...}, "feedback": {"text": "...", "claims": [...]}, "feedback_error": null}`.

**Errors.** One shape for every non-2xx response: `{"error": <code>, "message": <text for the learner>}`. FastAPI's own 422 body is replaced by this shape, so the front end parses one thing.

| Status | `error` | When |
|---|---|---|
| 422 | `invalid_input` | Empty or overlong text, unknown feature, bad JSON. `message` says what to fix. |
| 429 | `daily_limit` | The user has used their AI requests today. Adds `resets_at` (UTC midnight, ISO 8601) and a `Retry-After` header. |
| 503 | `spend_cap` | The day's global spend cap is reached. |
| 503 | `model_error` | The API failed after the client's retries, or the answer failed the schema. |

**Feedback is the exception:** it always returns 200 with the grade, and puts `daily_limit`, `spend_cap` or `model_error` in `feedback_error` (with `resets_at` if relevant). The grade is free and must always show (#107, #113).

**Pydantic** models live in `api/schemas.py` and convert from the dataclasses that `tutor` returns. `tutor` knows nothing about Pydantic or HTTP.

## Decision 2: Explain

**Input.** Letters, spaces and punctuation; at most **25 words** and 300 characters. A "word" is a run of letters (macrons allowed); punctuation and digits are dropped. Over the limit is a 422 before any API call.

| Option for N | Evidence | Assessment |
|---|---|---|
| 15 | Median sentence is 8 to 13 words in the three large treebanks. | Cuts off more than a quarter of ITTB sentences (its 75th percentile is 20). |
| **25** | 90th percentile is 22 (Perseus, PROIEL) and 27 (ITTB); 95th is 25 to 33. Measured on the train splits, punctuation excluded. | Takes about nine sentences in ten. Cost stays bounded. |
| 40 | Covers almost all. | Each extra word is a tool call and an output claim. Worst-case cost grows with it. |

**Model.** One word: `claude-haiku-5-5`. Two or more words: `claude-sonnet-5-5` (plan.md section 6). M3 measured one-word exact match with tools at 82.4% (Haiku) and 86.9% (Sonnet) on test, so a sentence, where the reading must also be judged, gets the stronger model.

**Prompt `explain-v1`** lives in `priscianus/tutor/prompts.py`. It pins the system prompt, the schema (ADR-004 Decision 1), the tools (`lookup_form`, `inflect`) and the limits below, and is bumped like `tools-parse-v1`. It runs `verify_and_repair` with ADR-004's defaults, so the app uses the pipeline M3 measured.

**Limits for sentences** (ADR-004 Decision 3 left this to M4): tool calls per round **25** (one per word), rounds 3 on the first pass, 1 on each repair attempt. API calls per request stay at most 8.

**What `text` holds:** 2 to 4 sentences of plain English: a rough translation and what each word does in the sentence. **`text` is not checked.** Only `claims` are verified. The prompt tells the model to put every statement about a word's form in a claim, and the screen labels `text` "Explanation (not checked)". Without this, a badge-less sentence could say something false about *amāvērunt* while the badges say "verified".

**Lining claims up with the words typed** (in `tutor/words.py`, no model involved):

1. Tokenise the input, keeping the typed spelling.
2. Walk the tokens in order. A claim matches a token if `key_loose(claim.form) == key_loose(token)`, or the token equals the claim's form plus `que`, `ne` or `ve` (*virumque* matches a claim for *virum*). Each claim is used once, so a repeated word takes its claims in order.
3. A token with no claim is listed with `claim: null` and `note: "not_explained"`. It is never dropped.
4. A claim that matches no token is dropped and counted in `dropped_claims`.

The prompt asks for the claim on the word without its enclitic. Code does not try to split words by itself: the index has no entry for *neque* or *amatne*, and stripping *-ne* from *neque* would find the verb *neo*. The enclitic gets `note: "enclitic -que"`.

**Reading choice is M5.** In M4 the model gives one claim per word, with no promise that it used the sentence. If the form has several readings the state is `ambiguous` and the badge lists the others. M4 does not say which one the sentence needs.

## Decision 3: Drills

**v1 has one drill type: "give the form".** The learner sees a lemma and features and types the form. "Decline *rēx* in the plural" is six such items (nominative to ablative, plural). Other types (choose the case, translate) are not in v1.

| Who does what | Model | Code |
|---|---|---|
| Understand the request, choose lemmas and features | Yes | No |
| Call `list_lemmas` and `inflect` to look at the index | Yes (as tools) | Runs them |
| Write the **expected answer** | **Never** | `inflect`, through the tool executor's path (same feature translation, same filter for `-`) |
| Write the item's prompt text | No | Yes, from lemma and features |
| Drop items with no form, remove duplicates, trim to `count` | No | Yes |

**Output schema.** `{"message": "", "items": [{"lemma", "pos", "features"}]}`, with the feature names and values of ADR-004. This deliberately differs from ADR-004 Decision 1's "every structured output is `{text, claims}`": a drill item says nothing about a form, so there is nothing to verify, and code computes the answer.

**Edge cases:**

| Case | Behaviour |
|---|---|
| Several forms (*amāvērunt*, *amārunt*, *amāvēre*) | All are accepted. Grading compares the answer with every form. |
| No index form (`NoSuchFormError`, unknown lemma) | The item is dropped. To avoid a second model call, the model is asked for `count + 5` items and code keeps the first `count` valid ones. Fewer valid items than asked gives `shortfall > 0`. |
| Defective word or deponent (*loquor* has no `Voice=Pass`) | Dropped if no form; the executor already relaxes what the index cannot record. |
| Impossible request ("1st person of a noun", unknown lemma) | `items: []` and a `message`. If every item is dropped, the code writes the message. |
| Duplicate (lemma, features) | Dropped. |

**Model and prompt:** `claude-haiku-5-5`, `drills-v1`. The seed for `list_lemmas` is a hash of the request text, so the same request gives the same lemmas.

**`list_lemmas`.** It becomes a tool for the drill model, and a method on `MorphologyIndex` and `SqliteIndex` (ADR-004 said "the interface grows with its callers"):

```python
def list_lemmas(
    self, *, pos: str | None = None, infl_class: str | None = None,
    deponent: bool | None = None, freq_band: str | None = None,
    limit: int = 20, seed: int = 0,
) -> list[LemmaInfo]:  # LemmaInfo(lemma, lemma_display, pos, infl_class, deponent, freq_band)
```

- Keyword-only filters; `None` means no filter. `limit` is capped at 50.
- Returns only lemmas with `base_lemma IS NULL` and at least one form that is not `-`.
- Sampling is `random.Random(seed)` over the matching rows sorted by id, so the same arguments give the same list. The pool is at most 34,935 rows, so reading ids is cheap.
- No gender filter (see Decision 4). The model may pick lemmas it knows, such as neuter nouns. That is safe: the item text is built by code, and the answer comes from `inflect`.

**Are accepted answers sent to the browser? No.** The item carries lemma and features only. `/api/grade` recomputes the accepted forms, so a changed item can only change the question, never the key. Seeing the key only after answering also stops a learner reading answers off the network tab.

**Free-text requests can carry instructions** ("ignore your rules and..."). The damage is bounded: output is checked against a schema, every item is checked by `inflect`, and the model has no tool that changes anything.

## Decision 4: Lemma metadata

### `infl_class` (done in #100)

Source: the Wiktextract dump, which the build already reads. I checked what it holds:

| Kind | Where the class is | Index lemmas with it (matched by spelling) | Value set |
|---|---|---|---|
| Verbs | The headword line (*"third (-iō variant) conjugation"*). The `la-conj` template gives `irreg` for 204 entries. | about 6,206 of 7,898 verbs without a `base_lemma` | `1`, `2`, `3`, `3io`, `4`, `irreg` |
| Nouns | `la-ndecl` argument, e.g. `rēx/rēg<3>` | about 16,225 of 16,514 | `1` to `5` |
| Adjectives | Headword line (*"first/second-declension"*, *"third-declension"*) | about 9,557 of 9,654 | `1-2`, `3` |

Two points where the plan and issue #100 are wrong:

- **`capiō` is not marked in `la-conj`.** Its argument is `3.sigm`. The `-iō` variant is only in the headword line, which is why #100 reads that line as `_is_deponent` already does. `ferō` is `irreg` in the template and "third conjugation, suppletive" in the headword line, so `irreg` wins.
- **Gender filter.** plan.md section 4 mentions "neuter 3rd-declension nouns". The index has no noun gender. The headword line has it for 15,701 of 16,697 nouns, so it could be added, but no M4 issue needs it. It is a follow-up (F2), and M4 drills do not filter by gender.

Lemmas whose source does not give a class stay `NULL`, never guessed. The counts above are approximate because lemmas that share a spelling were merged; #100 reports exact coverage.

### `freq_band`

| Option | Benefits | Downsides |
|---|---|---|
| **A. UD train splits, all six treebanks** (as ADR-003 does for the eval) | Already built. 10,797 lemma-and-POS entries. | Perseus, PROIEL and ITTB are CC BY-NC-SA. The app is public, and a subscription is possible (plan.md section 8). Ranks derived from them would sit in a CC BY-SA database, beside the licence note on `morphology.db`. |
| **B. The three CC BY-SA treebanks only** (LLCT, UDante, CIRCSE) | No non-commercial data. Compatible with the index's CC BY-SA 4.0. 5,031 entries from 96,926 tokens. | Smaller: 1,874 nouns, 1,500 verbs and 892 adjectives get a band (against 3,983, 2,661 and 1,793). LLCT is charter Latin, so it leans medieval. Only 775 of its top 1,000 are in the top 1,000 of option A. |
| C. A curated core list | Written for learners. | Needs a source with a clear licence, which I have not found. |
| D. Leave for later | No work. | "10 verbs" returns whatever is in the pool, mostly rare lemmas. |

**Decision: option B,** as a new issue (F1) before #101. Bands are `top1k`, `1k-10k` and `rare` (as ADR-003), averaged across treebanks (as `frequency_ranks` does). Drills ask for `top1k` unless the request names rare words. The eval's `parse-v1` bands, from all six, **are not changed**: a different source means a different list, so the evals never read this column. This is a judgement call: if option B's list gives odd drills, option C replaces it with no API change.

## Decision 5: Trust badges

One badge per claim. The label is always text, so colour is never the only signal. The colour pairs are dark text on a light tint; the contrast ratios were computed.

| State | Label | Icon (shape) | Text / tint | Contrast | Expands to |
|---|---|---|---|---|---|
| `verified` | Verified | Circle with a check | `#14532d` / `#dcfce7` | 8.3 : 1 | Nothing. The parse is shown in plain words ("dative singular of *rex*"). |
| `ambiguous` | Verified, N other readings | Circle with two arrows | `#1e3a8a` / `#dbeafe` | 8.5 : 1 | The other readings, one per line, in plain words. |
| `unverifiable` | Not in the database | Dashed circle with `?` | `#374151` / `#f3f4f6` | 9.4 : 1 | "The database does not hold this word, or it holds no adverbs, prepositions or conjunctions. It has not been checked." |
| `disputed` | Disagrees with the database | Triangle with `!` | `#7c2d12` / `#ffedd5` | 8.2 : 1 | The claim, then every reading the index has, and "The database can be incomplete. This may still be right." |

- **`disputed` is not red.** On the raw test runs, 58% of contradicted answers were correct (ADR-004), so the badge says "disagrees", not "wrong".
- The badge is a `<button>` with `aria-expanded` (only when it has something to show). Its accessible name carries the whole state: "Verified: matches the database. Show details".
- Icons are also different shapes, so the states differ for a person who cannot see colour. Text meets WCAG AA (4.5 : 1). Icon and border use the text colour, so they also pass the 3 : 1 rule for non-text parts.
- A UD-feature-to-English mapping (`Case=Dat` is "dative") lives in the front end (#110).

## Decision 6: Grading and feedback

**The index grades. No model is called in `/api/grade`.**

1. Server side, call the tool executor's inflect path for (lemma, features, pos). The accepted forms are never read from the request.
2. Normalise the answer and each accepted form with `morphology.normaliser.key_loose`: trimmed, lower-case, macrons removed, `v` folded to `u`, `j` to `i`, *æ* and *œ* expanded.
3. **Correct = the answer's key equals the key of any accepted form.**

| Option for macrons | Benefits | Downsides |
|---|---|---|
| **A. Optional and ignored** | A learner without a macron keyboard can play. The index writes the same lemma with different lengths (*canō*, *cānō*), so grading on them would mark correct answers wrong. | Does not teach vowel length. |
| B. Required | Teaches length. | Needs reliable macrons, which Wiktionary does not give. |

**Decision: option A.** The drill screen says "Macrons are optional" (#112). *amāvērunt*, *amaverunt* and *AMAVERUNT* are all correct, which I checked against `key_loose`.

**Wrong answers.** `lookup_form(answer)` lists what the typed form really is ("that is the 3rd person singular"). Same-lemma readings are flagged `same_lemma`. A form the index lacks gives an empty `answer_is`.

**Feedback is a separate endpoint,** `POST /api/feedback`:

| Option | Benefits | Downsides |
|---|---|---|
| A. A flag on `/api/grade` | One request. | Grade waits 2 to 4 s for the model. The endpoint is free and counted in one case. |
| **B. Own endpoint** | The grade shows at once and stays free. The screen then loads feedback, which can fail without hiding the grade. | Two requests. |

**Decision: option B.** `/api/feedback` takes the grade request, grades again itself, and tells the model the result. The model:

- is `claude-haiku-5-5`, prompt `feedback-v1`, schema `{text, claims}`, with the tools;
- is told the grade and what the typed form is. Whether the answer is right comes from the code only, so the text cannot change the grade;
- has its claims verified like explain's. `verify_and_repair` runs with `max_repairs=0`: the feedback is one or two sentences, so a repair call is not worth the cost, and a contradicted claim just shows `disputed`.

## Decision 7: Limits and cost

**Telling users apart.** The front end and the API will be on different domains (Decision 8), so a browser blocks a cookie set by the API in many browsers (third-party cookies).

| Option | Benefits | Downsides |
|---|---|---|
| A. Anonymous cookie set by the API | Familiar. | Blocked cross-site in Safari and others. |
| B. IP hash only | No client state. | Users behind one IP (a school) share a limit. |
| **C. Random ID in the browser's `localStorage`, sent as `X-Client-Id`, plus an IP-hash backstop** | Works cross-site. No cookie banner. The IP limit stops a user making new IDs. | Clearing site data resets a user's count, up to the IP limit. |

**Decision: option C.** The ID is a UUID the front end makes once. The API also hashes the client IP (`Fly-Client-IP`) with a secret salt, stores only the hash, and counts it too. **Per ID: 20 AI requests per UTC day** (plan.md section 8). **Per IP hash: 60.** Both are in env vars.

**Which requests count:** explain, drills, feedback. Not grade, not health. A request counts when it passes validation, and the count is given back if the model call fails (a 503).

**Where counters live:** `limits.db` (SQLite, table `usage(day, subject, count)`), on the same persistent volume as `llm.db`, so a restart does not reset it. It is a separate file, so the app never writes to the `LLMClient`'s database.

**Global daily spend cap:** `DAILY_SPEND_CAP_USD`, default **$2**. Daily spend is `SELECT SUM(usd) FROM call_log WHERE date(created_at) = date('now')` on `llm.db`. `created_at` is SQLite's `CURRENT_TIMESTAMP`, which is UTC, and cache hits log $0, so there is no second tally to drift. The check runs before the model is called. Concurrent requests can overshoot by about one request each.

| Request | Cost | Source |
|---|---|---|
| Explain, one word (Haiku) | about $0.0003 | Measured: $0.00034 per item, verified mode, 1,000-item test split. |
| Explain, one word (Sonnet) | about $0.005 | Measured: $0.00478. |
| Explain, 25-word sentence (Sonnet) | about $0.05, up to $0.10 with repair | **Estimate, not measured.** About 11,000 input and 3,000 output tokens at $2 and $10 per million. #117 records the real figure. |
| Drills, 10 items; feedback (Haiku) | about $0.001 to $0.003 | Estimate (plan.md section 8). |

The worst case for one user is 20 sentences, about $1 to $2 a day. $2 is about 40 full sentences or thousands of Haiku requests, and a ceiling of about $60 a month. The Anthropic account also gets a monthly limit (#116). This is a judgement: raise it when the real figures are in.

**Env vars:** `ANTHROPIC_API_KEY`, `ALLOWED_ORIGINS`, `MORPHOLOGY_DB`, `LLM_DB`, `LIMITS_DB`, `DAILY_REQUEST_LIMIT` (20), `IP_DAILY_LIMIT` (60), `DAILY_SPEND_CAP_USD` (2), `IP_HASH_SALT`.

## Decision 8: Deployment

**API host.** Prices below are from memory and unchecked; #116 confirms them.

| Option | Benefits | Downsides |
|---|---|---|
| **A. Fly.io** | Volumes (persistent disk) on small machines. A machine can stop when idle and start on request. About $3 to 5 a month. | A cold start of a few seconds after idling. More set-up (`fly.toml`, Dockerfile). |
| B. Render | Simple. | A persistent disk needs a paid always-on instance (about $7 a month); the free tier has none and sleeps after 15 minutes. |

**Decision: option A.** One small machine and one volume (1 GB) holding `morphology.db`, `llm.db` and `limits.db`. `ANTHROPIC_API_KEY` and `IP_HASH_SALT` are Fly secrets, never in the repo. `/health` is the health check.

**Front end:** a static Vite build, so Vercel and Netlify are equal here. **Vercel**, for its pull-request preview URLs. Its free tier is for non-commercial use (from memory), so a paid subscription later (plan.md section 8) means a paid plan or a move to Netlify. `VITE_API_URL` points to the API; the API's CORS allows that origin and the `X-Client-Id` header.

**Getting `morphology.db` to the server.**

| Option | Benefits | Downsides |
|---|---|---|
| A. Build it in the Docker image | One artefact. | The build needs the 1.3 GB dump, which is not pinned (the upstream file is regenerated). Each build could give a different index. |
| B. Upload it by hand to the volume | Simple. | Manual, and easy to get out of step with CI. |
| **C. A GitHub Release asset, pinned by SHA-256** | The same file for the server and CI. Publishing it is the CC BY-SA 4.0 "published copy" the licence note expects. | One extra, manual step per index change. |

**Decision: option C.** `src/data/index-release.json` holds the asset URL and SHA-256. The API's start-up script downloads the file to the volume when it is missing or the hash differs, and refuses to start if the hash is wrong. This is a new issue (F3), and the first release must come **after** #99, #100 and F1, because they change the build.

**`llm.db`** is on the volume. It is the call log and the cost source, so it must survive restarts.

**Attribution.** A footer on every screen (#109), worded as `DATA_LICENCES.md` requires: "Latin word data from Wiktionary (English Wiktionary contributors), CC BY-SA 4.0, extracted with Wiktextract (kaikki.org). The database built from it is also CC BY-SA 4.0." It links to the release asset. After F1 it adds: "Word frequencies from the LLCT, UDante and CIRCSE treebanks (CC BY-SA 4.0)."

## Decision 9: CI smoke eval

**Set:** 50 items from **dev** only. Test stays frozen. Dev has 22 cells (slice, class, band). The set is drawn with `parse_set.allocate` in the same shares as `parse-v1` (class 35/25/15/15/10, band 40/35/25) with a fixed seed, so it is stratified the same way. It is committed as `src/data/eval_sets/smoke-v1.jsonl`, a manifest of sentence and word IDs and hashes, with no treebank text.

**Mode and model:** `verified`, `claude-haiku-5-5`. It is the cheapest model and the pipeline the app uses.

**Metrics and threshold.** One metric alone is not enough: ADR-004 showed that deferring to the index lowers hallucination while accuracy falls.

| Metric | Fails the build when | Why |
|---|---|---|
| Hallucination count (final claims `disputed`) | more than **baseline + 3** items | It is what the issue asks the build to catch. |
| Exact match | below **baseline − 3** items (6 points) | Stops the build passing by agreeing with the index. |
| Schema failures | any | M3 had none (0 of 300 on dev), so one is a bug. |

With 50 items one item is 2 points. The margin of 3 items means a change of 6 points. For a count that averages 1 to 2 items, ordinary sampling variation passes the line only rarely (my estimate, not measured). The baseline is measured once, when #114 runs the committed set, and is stored in the one file that holds the thresholds. For reference, Haiku `verified` on all 300 dev items had 1.0% hallucination, and 4.3% on test.

**Cost.** A cold run is about 50 × $0.00034 = **$0.02**. The response cache (`llm.db`) is kept between runs, so a PR that changes no prompt costs $0. CI passes `--max-cost 0.50`.

**Index and treebanks in CI:**

- **The index:** `actions/cache` keyed on `index-release.json` (that is, on the SHA-256), filled from the release asset (Decision 8). I do not rebuild it in CI: the dump is not pinned, so a rebuild would not match the baseline.
- **UD treebanks:** `actions/cache` keyed on `download_ud_latin.py`, filled by `make eval-data`. The script pins SHA-256 for every file already.
- **The response cache:** `actions/cache` with a key that includes the run ID and `restore-keys` on the prompt files, since a cache entry cannot be overwritten.

## Decision 10: Code location

| Option | Benefits | Downsides |
|---|---|---|
| **A. A new `priscianus/tutor/`** next to `pipeline/` | `api/` stays HTTP only. Tutor logic can be tested without a server. | One more package. |
| B. Logic in `api/` | No new package. | Tests need `TestClient`. Evals and CLI cannot reuse it. |

**Decision: option A.**

```
src/backend/priscianus/
  tutor/
    words.py        # tokenise, line up claims with words (Decision 2)
    explain.py      # explain(text) -> ExplainResult
    drills.py       # make_drills(request, count) -> DrillSet; expected_forms(item)
    grade.py        # grade(item, answer) -> Grade
    feedback.py     # feedback(item, answer, grade) -> Feedback
    prompts.py      # explain-v1, drills-v1, feedback-v1 and their tool definitions
  api/
    main.py         # app, lifespan: one index and one LLMClient per process
    schemas.py      # Pydantic models, conversion from tutor's dataclasses
    routes.py       # the five endpoints
    errors.py       # the error shape and handlers
    limits.py       # per-user and per-IP counters, daily spend (Decision 7)
    settings.py     # environment variables
  morphology/       # gains list_lemmas
```

Dependencies run one way: `api` → `tutor` → `pipeline`, `verifier`, `morphology`, `llm`. `tutor` never imports `api`. **Mypy strict:** `priscianus.tutor.*` and `priscianus.api.*` are added to the strict overrides with `morphology`, `verifier` and `pipeline`. I expect `api` to need a few casts; if it fights FastAPI, drop `api` from strict and keep `tutor`.

## Consequences

- **A public app needs a real cost bound.** The $2 cap and the per-user limit are the only protection, and the sentence cost is an estimate until #117.
- **`text` is not verified.** The screen says so. A learner reading only the prose gets no badge.
- **Explain gives one reading per word.** For *rēgī* M4 will show "Verified, 1 other reading" and not say which fits. Context is M5.
- **Repair is on for explain, as in `verified`.** M3 found it nearly neutral (test: 4 items fixed and 1 made worse, for about 6 to 8% more cost). A sentence has many claims, so repair may trigger often. #117 reads the rate from the call log; if repair costs more than it fixes, set `max_repairs=0`.
- **The smoke eval tests the one-word pipeline, not `explain-v1`.** It guards the verifier, tools and repair. It does not guard sentence explanations or drills. Those are checked by unit tests and by hand.
- **The index must be published before the first deploy,** and every index change repeats that.
- **M3 numbers were measured on build `8081e7a9`.** After #99 the build changes (#99 notes the new hash).
